# IT access request intake build plan

## Choices

- **Runtime** — Python 3.11+ with a standard-library validator for the supplied schema and SQLite on the intake host. The starter already uses Python, and SQLite transactions can keep jobs, attempts, and current records consistent across concurrent CLI processes.
- **Interface** — A CLI on one shared Linux host, accessible to regional operators over SSH. Operators can run `python3 -m intake start <batch-dir>`, `python3 -m intake queue`, `python3 -m intake pending`, `python3 -m intake history <document_id>`, `python3 -m intake resume`, `python3 -m intake retry <document_id>`, and `python3 -m intake refresh` against the same local database. A separate CLI process can read during intake.
- **Test command** — `env -u API_KEY python3 -m unittest discover -s tests -v` follows the starter and supports deterministic subprocess, clock, and transport checks without a model credential.
- **Model provider** — Support OpenAI Responses over HTTPS with strict structured output using the supplied schema, configurable model ID (initial choice `gpt-4.1-mini`), output limit and timeout, and a bearer credential from `API_KEY` for live runs. Inject a fixture-backed provider or mock HTTP transport for all development checks. The brief leaves the provider open, so confirm the facilitator key works with the selected provider before any optional live run. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)

## Steps, in build order

Write each named test first, run it with `API_KEY` unset, and record its failure against the missing behavior before implementing the step. Then run the full mock-only suite. The case IDs below identify the tests in the test plan. Fixture names describe saved replies or named variants derived from them in tests. The checked-in mock responses are deterministic and the expected-fact register is authored before scoring.

1. **Build the mock provider** (R-81). Write **T01 Mock provider** first. Build the application's injectable provider interface and disk-backed mock, using the starter's fixture directory. Reuse the completed starter step. Return saved envelopes, surface scripted failures, and record calls per document. Support controllable delays and sequential replies so later tests can model refreshes, timeouts, and overlapping workers deterministically.
2. **Read exports and validate extracted facts** (R-08–R-29). Write **T02 Message boundary**, **T03 Schema and evidence validation**, and **T04 Source rules** first. Read original UTF-8 bytes, derive the filename and byte hash, and pass the entire decoded message to the provider under a versioned extraction prompt. Validate the response completion state and supplied schema before accepting data. Check date format and exact source quotes. Preserve the stated ID, add a mismatch issue when applicable, and keep documents keyed by filename. Instruct the model to preserve explicit facts, report each absent or unresolved scalar, quote conflicts, honor labelled corrections, leave relative dates unresolved, and extract the requested permission in a change. Keep message content in a data field distinct from the prompt. Interpret issue prose by substance in checks.
3. **Apply the review policy** (R-30–R-42, R-66–R-69). Write **T05 Complete request**, **T06 Missing dates**, **T07 Conflicting details**, **T08 Embedded instructions**, and **T09 Rule precedence and route matrix** first. Route validated facts and source evidence through the ordered policy rules in application code. Recognize and preserve override attempts, verify that the cited evidence comes from the source, and derive the route independently of model-supplied routing or approval directives. Record only human review next steps. Surface manager as a contact and describe how Security Review hands off its recommendation.
4. **Record source revisions and attempts** (R-06, R-07, R-43–R-48, R-71, R-72). Write **T10 Unchanged rerun**, **T11 Changed source content**, and **T12 Omission and settings refresh** first. Use immutable source revisions and append-only outcomes with a single current-attempt pointer per filename. Publish the outcome and current pointer together. Match reusable successes by source bytes and effective provider, model, request settings, prompt, schema, and policy identifiers, with mock and live configurations kept distinct. Reuse the current result only after a successful attempt with a matching fingerprint. Ordinary intake updates only named documents. Add an operator refresh that compares fingerprints for stored sources under the selected configuration and requeues affected documents, including those no longer in an input directory. A policy revision fingerprint includes the office policy content and routing configuration. Persist redacted effective configuration and version identifiers with each attempt for `history`.
5. **Expose shared intake, progress, and recovery through the CLI** (R-01–R-05, R-41, R-53, R-85). Write **T13 Incremental review and resume**, **T14 Overlapping intake**, and **T15 CLI intake and surge check** first. Persist the batch's source bytes and job list before starting calls. Use bounded workers and a shared configurable cap on active provider claims across CLI processes, with a default of four so one slow call leaves capacity for others. Claim work in short database transactions and call the provider outside them. Coalesce identical in-flight jobs. Order updates by a database-assigned generation so late older work stays in history and cannot overwrite a newer published attempt. Use expiring claims that cover the configured call deadline, with claim tokens to resume abandoned work and prevent a superseded worker from publishing. Resume with the saved processing configuration and require the corresponding policy, prompt, and schema versions to be available. Surface a version mismatch as pending work with a clear path to refresh it under the installed versions. Display work state and terminal queue routes through separate commands, with the latest finished attempt visible while a replacement is pending. Document that a crash can repeat an uncommitted model call.
6. **Implement the live adapter and actionable failure path** (R-49–R-57, R-60, R-61, R-70, R-73, R-74). Write **T16 Provider failure**, **T17 Refusal or interruption**, **T18 Failed retry after prior success**, and **T19 Provider contract and redaction** first. Send the model, strict schema, extraction prompt, and message through the transport seam. Reject non-completed, refused, malformed, and invalid responses before routing. Record a per-document error with a sanitized reason and retry command after a failed call. Leave provider failures visible for explicit retry so a provider outage cannot trigger an unbounded retry loop. Keep other work running. Make explicit retry a new attempt that can bypass reuse, including a forced retry after success. A failed newer attempt becomes the current error and leaves the previous valid attempt available in history. Package the application, prompt, schema, and locked dependencies.
7. **Export the review snapshot and request evidence** (R-62–R-65, R-83). Write **T20 Submission artifacts** first. Add `python3 -m intake export --out <new-directory>` to produce the JSONL, queue JSON, and redacted request evidence from a single consistent read of a selected database. Write into staging and publish the directory only after all files are ready. The operator CLI continues to read current state from SQLite. Generate the checked-in snapshot in `deliverables/` from an isolated, fully processed mock run of the supplied 20, and keep its extraction and queue files together in the submission commit. Derive request evidence from the adapter's real request construction and document the implemented response-handling path.
8. **Compare extraction accuracy against source-derived expectations** (R-75–R-82). Write **T21 Paraphrased synthetic request** and **T22 Accuracy comparisons** first. Author expected fields for all 20 supplied messages plus the paraphrase, with source evidence, before looking at the outputs to be measured. Keep those expectations independent of the mock replies and publish them in `deliverables/accuracy.md`. Run `python3 -m intake accuracy --provider mock` and report matched fields over 12 scalar fields × 21 cases, including nulls, with missing records, invalid output, and error records counting as zero matches for the affected case. Source-derived expectations live in a table in the accuracy deliverable, separate from the saved response fixtures. Compare dates and categories in their policy representations, and define concrete expected purpose phrases before the run. Report exact purpose-string differences and distinguish equivalent wording from factual errors. Check quote grounding and issue substance separately from the scalar score. Label each recorded run with its response origin and effective configuration.
9. **Verify the documented handover** (R-55, R-58–R-60, R-81, R-84–R-87). Write **T23 Operator handover** first. From clean local state, check setup and the exact README commands for mock intake, queue inspection, pending work, history, resume, retry, refresh, export, tests, and accuracy. Document the supported provider and configuration, the one-host assumption, ordinary and surge workloads, the shared worker cap, variable provider availability and rate limits, the interruption behavior, and what the mock tests establish. Record commands, assertions, intended comparisons, and actual observations or repairs in `deliverables/verification.md`.
